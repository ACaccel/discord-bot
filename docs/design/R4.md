## 1. 概要

R4 處理「handler `index.ts` 肥大、純函式與 Discord I/O 混在一檔」這條技術債。
動機與要達成的事項詳見 [proposal §7](../proposal.md)；分層觀點與規則放在 handler
同目錄而非 `shared/` 的理由見 [HLD §7](../high-level-design.md)。

本詳細設計只回答三個問題：

1. 4 個示範 handler 要怎麼拆——抽出哪些 helper、留下什麼、目標行數。
2. ESLint 規則的精確設定——選哪條規則、glob 範圍、為什麼。
3. 4 份文件要插入的規範文字——逐字、4 份完全相同。

不重抄 proposal 的「不做」清單；§10 僅針對 R4 重申。

---

## 2. 設計目標

衍生自 proposal §7.4 驗收與 HLD §7.1 handler 結構準則：

- 4 個示範 handler 的 `index.ts` 全部 ≤ 150 行（含 import 與 JSDoc）。
- 抽出的每個 helper 為純函式（pure，無 I/O、無 Discord 物件依賴）或受控副作用（接受抽象 seam），且可獨立寫單元測試。
- `index.ts` 仍保留 handler 本職：interaction input 抽取、權限與 guild repos 檢查、Translator 呼叫、回覆組裝。
- `max-lines` ESLint 規則對全部 `src/handlers/**/*.ts` 為 error；現存超標檔在本輪一併處理或於 PR 中明列 follow-up。
- 行為位元等價：既有 handler 測試全綠，沒有任何 Discord 指令簽名或 i18n key 變更。

非目標：

- 不對 `src/handlers/**` 全樹做一次性掃蕩拆分。
- 不對 plugin / core / persistence 套用同一行數門檻。
- 不引入 cyclomatic complexity / function-length / max-params 等其他 lint 規則。

## 3. Handler 內部結構準則

依 HLD §7.1 形式化，落地到 codegen 與 IoC 既有契約：

### 3.1 `index.ts` 必須保留的內容

`src/handlers/<type>/<name>/index.ts` 是 codegen 的單一入口
（`scripts/gen-registry.ts` 透過資料夾名稱掃出 default export），
所以下列項目必須留在 `index.ts`：

- `export default class <name> extends Command`（或 Button / Modal / SelectMenu / Reaction 基底類別）。
- `constructor` 中的 `this.setConfig({...})`——Discord 指令簽名定義。
- `execute(interaction, bot)` 方法本體，但僅做：
  - 從 `interaction.options` 抽 input 並做最小型別轉型；
  - guild / repos / 權限檢查；
  - 呼叫 helper 完成 domain 計算；
  - 呼叫 `bot.translator.t(...)` 取 i18n 字串；
  - 把結果組裝成 Discord 回覆物件（`editReply` / `followUp` / `showModal` / `AttachmentBuilder`）；
  - 在最外層 `try/catch` 把 `DomainError` 交給 `replyForError`。

### 3.2 必須抽出的內容

- 純資料計算（日期解析、字串清理、聚合計算、排序、分塊）。
- 任何不涉及 Discord 型別、只進出 primitive / domain DTO 的函式。
- 大型常數表（如 `PROVIDER_CHOICES`）若超出單純列舉、有資料結構意涵，抽到 `<helper>.ts`。

### 3.3 可以抽出但不強制

- 涉及 Discord builder 物件（`ModalBuilder` / `EmbedBuilder` / `AttachmentBuilder`）的「組裝程式碼」可抽出
  為 `build-<thing>.ts`——它仍依賴 Discord 型別，但只要 `index.ts` 因此能落在 150 行內、且 helper 本身是函式而非 method，就可抽。
  此類 helper 簽名不必純，但測試以「給定參數→產出物件結構正確」為單元測試焦點。

### 3.4 helper 檔的可見性與命名

- helper 檔放在 handler 同目錄（sibling files），不放在 `src/handlers/shared/` 或 `src/handlers/commands/_helpers/`——HLD §7.2 已定論。
- helper 檔以 kebab-case 命名（與既有 `reply-for-error.ts`、`require-guild-repos.ts` 一致），對應的 `export` 為 camelCase 函式名或 PascalCase 型別名。
- helper 一律具名 `export`；不使用 `export default`（codegen 只認 `index.ts` 的 default export）。
- helper 之間若有共用型別，可額外加 `types.ts`；不得增設新目錄。

## 4. ESLint 規則設計

### 4.1 規則設定

於 `eslint.config.mjs` 末段（在 test/scripts override 之前）新增一個獨立 config block：

```js
// Handler 行數上限：強制 R4 的「index.ts ≤ 150 行」規則。
// glob 涵蓋整個 src/handlers/**，但排除 codegen 產出，避免誤殺
// registry.generated.ts（內含一行 import per handler，極易超標）。
{
  files: ['src/handlers/**/*.ts'],
  ignores: ['src/handlers/**/registry.generated.ts'],
  rules: {
    'max-lines': [
      'error',
      { max: 150, skipBlankLines: false, skipComments: false },
    ],
  },
},
```

**為什麼選 `max-lines`（per-file）而非 `max-lines-per-function`：**

- proposal §7.2C 與 HLD §7.3 的門檻單位是「`index.ts` 行數」，是檔案級概念，不是函式級。
- handler 的 `execute` 邏輯本來就會被切到多個 helper 函式，per-function 上限無法擋住「在同一個檔案塞 5 個 30 行的助手函式」的退化路徑。
- `max-lines` 計算包含 import 與 JSDoc，正符合 proposal §7.2B 第 1 條「150 行含 import、含 JSDoc」的措辭。

**為什麼 `skipBlankLines: false`、`skipComments: false`：**

- 與 proposal §7.2B 第 1 條一致：所有可見的視覺行都算進去。允許 skip 等於開後門。

**為什麼 `registry.generated.ts` 排除：**

- 已在頂層 `ignores: ['**/*.generated.ts']` 中被忽略；本 block 顯式重申是為了 self-documenting，避免日後有人縮減頂層 ignore 範圍時誤觸發。

### 4.2 既有 handler 過門檻清單

於 `src/handlers/**` 跑 `wc -l`（排除 `*.generated.ts`）目前超過 150 行的檔案：

| 檔案                                   | 行數 | 處置                                                                                                                                                                                                                                  |
| -------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `commands/db_list_message/index.ts`    | 320  | §5.1 本輪示範拆分。                                                                                                                                                                                                                   |
| `commands/inspect_member_ids/index.ts` | 172  | §5.2 本輪示範拆分。                                                                                                                                                                                                                   |
| `commands/emoji_frequency/index.ts`    | 158  | §5.3 本輪示範拆分。                                                                                                                                                                                                                   |
| `commands/ai_settings/index.ts`        | 158  | §5.4 本輪示範拆分。                                                                                                                                                                                                                   |
| `commands/command.ts`                  | 184  | 基底類別 + `localizeCommandConfig`，全為型別宣告與單一函式；屬於「handler 框架定義」而非單一 handler。本輪在 ESLint config 中以 `ignores` 個別放行，並於 R4 PR description 列為「框架檔，未來若需要拆分時再做（無功能複雜度問題）」。 |
| `reply-for-error.ts`                   | 157  | 跨 handler 共用 error→reply 對應；本身為單一 default-export 函式，行數絕大部分為 i18n key 對應表。同樣以 `ignores` 個別放行，PR description 列為 follow-up：考慮把對應表抽到 `error-reply-map.ts`。                                   |

上述「框架 / 共用工具檔」的 `ignores` 加在同一 block：

```js
ignores: [
  'src/handlers/**/registry.generated.ts',
  'src/handlers/commands/command.ts',
  'src/handlers/commands/discord-helpers.ts',
  'src/handlers/reply-for-error.ts',
],
```

每筆 ignore 必須在 ESLint config 同檔附行內註解標示「為何放行」與「follow-up 票號 / PR description 段落」。

## 5. 4 個示範 handler 拆分計畫

### 5.1 `db_list_message`

#### 5.1.1 現況

`index.ts` 320 行。組成：型別別名 + 7 個 helper 函式（`isValidDateString`、
`parseDateParts`、`parseStartEnd`、`buildReactionText`、`sanitizeMentions`、
`getDisplayName`、`truncateDisplayName`）+ Command 類別（`setConfig` 約 32 行、
`execute` 約 180 行）。`execute` 內混入訊息聚合、display name 解析、輸出分塊、
attachment / inline 兩種輸出模式。

#### 5.1.2 抽出計畫

| 新檔                          | 責任                                                                       | Signature                                                                                                                                                                                                |
| ----------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parse-range.ts`              | 純函式：把 `date` + `hour?` 解析成 `{ startMs, endMs }`，無效輸入回 `null` | `export const parseStartEnd: (date: string, hour: number \| null \| undefined) => { startMs: number; endMs: number } \| null`                                                                            |
| `render-reactions.ts`         | 純函式：把 schema 上的 reaction 物件渲染為 `<a:name:id> x12` 字串          | `export const buildReactionText: (reaction: NonNullable<MessageDoc['reactions']>[number]) => string`                                                                                                     |
| `sanitize-mentions.ts`        | 純函式：對輸出文字消解 `@everyone` / user / role mention                   | `export const sanitizeMentions: (text: string) => string`                                                                                                                                                |
| `format-message-lines.ts`     | 純函式：給定 messages + displayName resolver，產出 `string[]`              | `export const formatMessageLines: (messages: ReadonlyArray<MessageDoc>, opts: { resolveDisplayName: (userId: string, fallback: string) => Promise<string>; truncateAt?: number; }) => Promise<string[]>` |
| `chunk-output.ts`             | 純函式：把行陣列依 Discord 2000 字限制切塊（含 newline 計算）              | `export const chunkLines: (lines: ReadonlyArray<string>, maxLen?: number) => string[]`                                                                                                                   |
| `build-archive-attachment.ts` | 用 `AttachmentBuilder` 包成 txt 附件（依賴 Discord builder，非純）         | `export const buildArchiveAttachment: (params: { channelId: string; date: string; hour: number \| null \| undefined; text: string }) => AttachmentBuilder`                                               |

`format-message-lines.ts` 內部；`getDisplayName` 需要 `Guild` 與 cache map，

#### 5.1.3 預期 LOC

- `index.ts`：約 110–125 行（setConfig 32 + execute 約 70 + imports 約 15）。
- 各 helper 檔：`parse-range` 約 40、`render-reactions` 約 20、`sanitize-mentions` 約 15、`format-message-lines` 約 75、`chunk-output` 約 25、`build-archive-attachment` 約 18。

## 6. Design Pattern 採用

| Pattern                          | 採用點                                                                                                                                | 理由                                                                                                                                              |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Extract Method（refactoring）    | 4 個 handler 都把 `execute` 內的內聯邏輯抽成具名函式                                                                                  | proposal §7 要的就是這項；不引入新抽象，純粹搬遷                                                                                                  |
| Pure function isolation          | helper 公開介面避免 `interaction` / `Guild` / `GuildMember` 等 runtime 物件作為參數；Discord builder 仍允許在「build-\*」 helper 出現 | 測試成本最低；helper 與 Discord SDK 版本變動解耦                                                                                                  |
| Co-location（sibling file 原則） | 抽出的 helper 必須放在 `src/handlers/<type>/<name>/` 同目錄，不放 `shared/`                                                           | HLD §7.2：抽出物是 handler 內部實作細節；放 shared 區會誘導跨 handler 共用 → 形成隱性耦合。codegen 以資料夾名 = 指令名，同目錄不破壞 codegen 假設 |
| Strategy / Repository（沿用）    | 既有 Repository / Translator / LLMProvider 抽象在 R4 沿用                                                                             | 抽出的 helper 接收 `Repos` 介面或 `Translator` 介面，測試可注入 fake                                                                              |

不採用：

- 不導入 Command Bus / Mediator——範圍蔓延。
- 不把 4 個 handler 改寫成 Use Case + Presenter 分層——超出 proposal §7 範圍，且其他 handler 維持現狀會造成不一致。

下列段落以「**完全相同的措辭**」插入下列 4 份文件。任何一份文件被修改，另外
3 份必須同步——使用 `grep -F "Handler 行數規範"` 可一次找出全部出現點。

插入位置：

- `CLAUDE.md`：放在「Key abstractions › Handler codegen」段落之後，新增一個 `### Handler 行數規範` 三級小節。
- `CONTRIBUTING.md`：放在「新增 slash command」recipe 之後，新增一個 `### Handler 行數規範` 三級小節。
- `.claude/skills/project-conventions/SKILL.md`：放在「handler codegen」相關規則之後。
- `.claude/skills/coding-standards/SKILL.md`：放在「Clean & Readable Code」段落之後。

逐字內容：

```markdown
### Handler 行數規範

`src/handlers/<type>/<name>/index.ts` 必須遵守下列五點。新 handler 自第一行
程式碼起就套用，不留「未來再說」空間。

1. **`index.ts` 行數上限為 150 行**（含 import、含 JSDoc、含空行）。由
   `eslint.config.mjs` 的 `max-lines` 規則對 `src/handlers/**/*.ts` 強制執行，違規為 error。
2. **超出上限的 pure helper（純函式、不依賴 Discord 物件）必須抽到同目錄的獨立檔案**。
   檔名 kebab-case（例：`parse-range.ts`、`render-reactions.ts`），具名 `export`，
   不使用 `export default`。
3. **不可為了壓縮行數而把 Discord I/O、權限檢查、Translator 呼叫拆出 `index.ts`**。
   這四項是 handler 的本職：interaction input 抽取、guild / repos / 權限檢查、
   `bot.translator.t(...)` 呼叫、把 domain 結果組裝成 Discord 回覆物件。它們必須
   留在 `index.ts` 內。
4. **抽出的 helper 必須有對應單元測試**，置於 `test/unit/handlers/<name>/<helper>.test.ts`。
   純函式測試 happy path + 邊界 + error path；接受 Translator / Repos 的 helper
   注入 in-memory fake。
5. **helper 不可放在 `src/handlers/shared/` 或新增的共用目錄**——抽出的內容是該
   handler 的內部實作細節；若日後有第二個 handler 需要同一邏輯，再評估是否上提。
```

## 8. 測試設計

依 design.md §2.4 的「驗收點 / Fixture / 整合面」三段結構。

### 8.1 測試驗收點

對應 §5 各 helper：

**`db_list_message`**

- `parseStartEnd`：
  - `('2026-05-23', null)` → 回 full-day 區間，`endMs - startMs === 86_400_000`（受夏令時影響時改驗時區位移）。
  - `('2026-05-23', 14)` → 回 `[14:00, 15:00)`，`endMs - startMs === 3_600_000`。
  - `('2026-13-01', null)` / `('not-a-date', null)` / `('2026-05-23', 24)` → `null`。
- `buildReactionText`：custom emoji 帶 id+name → `<:name:id>`；animated → `<a:...>`；只有 unicode name → 回 name；都缺 → `[unknown_reaction]`。
- `sanitizeMentions`：`@everyone` → `@​everyone`；`<@123>` → `@user(123)`；`<@&456>` → `@role(456)`；無 mention 字串原樣返回。
- `chunkLines`：總長 < maxLen → 單 chunk；超過 → 切多 chunk 且每 chunk ≤ maxLen；空輸入 → `[]`。
- `formatMessageLines`：注入 stub `resolveDisplayName` 回傳固定值；驗 attachment / sticker / reaction 行的格式；驗 `[empty]` placeholder。
- `buildArchiveAttachment`：給定參數 → 回 `AttachmentBuilder`，檔名符合 `db_list_message_<channelId>_<date>_<hourLabel>.txt`。

**`inspect_member_ids`**

- `parseIds`：含多個 ID 字串 → 去重保留順序；無 match → `[]`；含 16 位數（不足 17）→ 過濾掉。
- `fmtTimestamp`：`null` / `undefined` → `'N/A'`；有效 Date → `<t:unix:F> (<t:unix:R>)`。
- `toText`：`null` / `undefined` / 空白字串 → `'N/A'`；其他原樣字串化。
- `truncate`：未超過 → 原樣；超過 → 結尾 `...` 且總長 = max。
- `buildMemberDescription`：四個分支——`user=null,member=null`、`user only`、`member only`、`both` —— 每個分支驗對應字段是否出現；注入 stub `t` 回 `${key}` 以便斷言 i18n key 串接正確。

**`emoji_frequency`**

- `clampOptions`：`topN=50` → clamp 至 30；`lastNMonths=36` → clamp 至 24；合法值原樣。
- `initEmojiCounts`：給定 emoji 字串陣列 → 回 Map（text/reaction）全部以 0 初始化。
- `accumulateEmojiCounts`：注入 messages fixture（含 content 內 `<:foo:1>` 與 reactions 含 `bar:2 count=3`）→ 對應計數正確；不在初始 Map 的 emoji 被忽略。
- `rankEmoji`：
  - `type='animated'` 只回 `<a:...>` 開頭；`'static'` 只回 `<:...>`。
  - `frequency='desc'` 回前 N 大；`'asc'` 回前 N 小。
  - `topN > 實際數量` → 回實際數量，不報錯。
- `formatLeaderboard`：給 25 筆 ranked → 每 `pageSize=10` 切一頁，最後一頁可少於 pageSize；header 行只出現在第一頁。

**`ai_settings`**

- `checkAiSettingsReady`：
  - `doc=undefined` → `{ ok: false, reason: 'no_doc' }`。
  - `doc=有效, modelOptions=[]` → `{ ok: false, reason: 'no_models' }`。
  - `doc=有效, modelOptions=['gpt-4']` → `{ ok: true, doc }`。
- `buildSettingsModal`：給合法輸入 → 回 `ModalBuilder` 實例；驗 `customId === 'ai_settings|<provider>'`；驗 4 個 LabelBuilder 都被加入；驗 `default` 選項對應 `current.model` 與 `current.web_search`。

### 8.2 Fixture / Mock 策略

- 純 helper（`parseStartEnd`、`buildReactionText`、`sanitizeMentions`、`chunkLines`、`parseIds`、`clampOptions`、`accumulateEmojiCounts`、`rankEmoji`、`checkAiSettingsReady`）：**無 mock**，直接呼叫並斷言。
- Translator-touching helper（`formatLeaderboard`、`buildMemberDescription`、`buildSettingsModal`）：注入 `TFn` stub `(key, params) => params ? `${key}:${JSON.stringify(params)}` : key`，斷言 i18n key 串接正確、避免去動真正的 i18next 載入。
- Repository-touching helper：本輪沒有抽出 repo-aware helper（repo 呼叫保留在 `index.ts`），所以 fakeRepos 不在 helper 層使用。
- Discord builder helper（`buildArchiveAttachment`、`buildSettingsModal`）：使用真實 `AttachmentBuilder` / `ModalBuilder` 物件並透過其公開 getter 斷言；不 mock Discord SDK。
- `formatMessageLines` 的 `resolveDisplayName`：以 in-memory map 提供 stub `async (id, fallback) => fixtureMap.get(id) ?? fallback`，避免實際 `Guild.members.fetch`。

### 8.3 整合面

- handler `index.ts` 本身的行為等價由**既有的 handler-level integration test** 覆蓋——只要 R4 不改變外部簽名與 i18n key，原測試應全綠。本輪不新增 handler-level integration test。
- 新 helper 單元測試置於 `test/unit/handlers/<name>/<helper>.test.ts`，與 handler 同名子目錄；不重用 `test/integration/`。
- CI gates：在 typecheck 與 unit test 同階段執行；`yarn lint` 必須對 `max-lines` 規則綠燈才視為通過。

## 9. 與其他 R 的整合點

### 9.1 R3 — `eslint.config.mjs` 改動衝突避免

R3 與 R4 都會修改 `eslint.config.mjs`：

- R3 在 plugins ↔ core/ioc 對齊的 `no-restricted-imports` block 增加 `src/plugins/**` 受限規則。
- R4 新增獨立的 `files: ['src/handlers/**/*.ts']` block。

兩者在 ESLint flat config 中是「同層級不同 entry」，彼此不互相 override；
合併順序為 R3 在前、R4 在後（因實作順序 R1→R2→R3→R4），R4 commit 應在 rebase R3 完成後再進；
若 R3 commit 動到 ignore 頂層列表，R4 commit 必須 rebase 上去後再驗證 `src/handlers/**/registry.generated.ts` 仍被忽略。

### 9.2 R6.3 — `no-console: error`

R6.3 把 `no-console` 從 `warn` 升為 `error`。

- 與 R4 的 `max-lines` 完全不衝突——兩者是獨立規則。
- 但 R4 的示範拆分過程若意外引入 `console.log` 除錯語句必須在送出 PR 前移除（R6.3 一旦合併，會 lint fail）。

### 9.3 R5 — i18n catalog 路徑反耦合

無直接整合面。R4 helper 的 `TFn` 介面是 type alias，不觸碰 `catalog-loader.ts`。

## 10. 不做的設計決策

重述 proposal §7.3 並補上 R4 設計層級的限制：

- **不對 `src/handlers/**` 全樹做一次性掃蕩拆分\*\*。除 4 個示範 + §4.2 列出個別放行的 3 個框架/共用檔之外，其他 handler 維持現狀；自然觸碰時順手收斂。
- **不對 plugin / core / persistence / infra 套用同一 150 行門檻**。這些層的「行數=複雜度」對應關係不同（如 `LLMProvider` 介面實作天然較長），套同一規則會誘導不必要拆分。
- **不引入 cyclomatic complexity / max-lines-per-function / max-params 等其他 ESLint 規則**。範圍蔓延風險，且本輪沒有客觀數據支持門檻設定。
- **本輪不再下調行數上限**。150 行是依現況 4 個示範拆分後的舒適區間設定；下調至 100 行會強迫過度切割。
- **不引入 `src/handlers/shared/` 或 `src/handlers/_helpers/` 共用目錄**。HLD §7.2 已定論：抽出的 helper 是內部實作細節，跨 handler 共用機率低；若日後真有第二個 handler 需要同一邏輯，再評估是否上提，且上提時應提到 `src/core/<domain>/` 或對應的 domain 模組，而非 handler 樹內的共用區。
- **不改 Discord 指令簽名與 i18n key**。`setConfig` 內容、`commands:*` / `replies:*` / `errors:*` 的 key 一律保留；R4 僅做 internal refactor。
