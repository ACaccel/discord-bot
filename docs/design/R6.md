## 1. 概要

R6 是 architecture-overhaul 收尾的「低優先單點修正集合」，本文件把
proposal §9 與 HLD §9 列出的 5 個子項各自展開為可實作的 design unit。

涵蓋：

- **R6.1** `traceId` 來源由 `Math.random()` 換為 `crypto.randomUUID()`。
- **R6.2** `BaseBot.login()` 失敗改為 reject（中止 `run()`）。
- **R6.3** 全 `src/` 殘餘 `console.*` 清除 + ESLint `no-console` 提至 `error`。
- **R6.4** `BaseBot` Handler Map 命名一致化（複數）、區域 / 欄位 snake_case → camelCase。
- **R6.5** `src/bot/index.ts` import 區段連續化，搬走中夾的 `sharedConnectionManagers`；ESLint `import/first` 提至 `error`。

範圍外（在 §11 重申）：不換 logger、不引入 `AsyncLocalStorage`、不對
`BaseBot` 以外的 snake_case 進行 R6.4 範圍的自動改名。

---

## 2. 共通設計原則

本文件繼承 [design.md §2](../design.md) 共通契約，僅補充 R6 特有的：

- **每個子項即一個 design unit**：可獨立 commit、獨立 review、獨立回退。
- **commit 粒度**：建議 5 個獨立 commit，commit message prefix 統一
  `refactor(R6.x): …` 以便日後查找。
- **無 design pattern 引入**：R6 全是 in-place 改寫；不新增類別、不新增
  抽象、不新增模組。
- **測試**：R6.1 / R6.2 各新增 1 個 spec；R6.3 / R6.4 / R6.5 完全靠
  ESLint + TypeScript compiler + 既有 431 個測試覆蓋。
- **時機相依**：R6.4 / R6.5 須與 R1 同分支同步落地（避免兩次大 diff）；
  R6.1 / R6.2 任意；R6.3 排在 R6 最後一項（避免在 R6.1 / R6.2 過程中
  又寫入新的 `console.*`）。

## 3. R6.1 — `traceId` 使用 `crypto.randomUUID`

### 3.1 現況

`src/bot/index.ts` 約 902 行（router middleware 取 traceId 處）：

```ts
const traceId = Math.random().toString(36).slice(2, 10);
```

問題：`Math.random()` 在高並發下 8 字元字元集（36 進位）的碰撞機率
顯著（生日問題下 ~10^4 筆即可期望出現碰撞），失去 traceId 的唯一性
本意。

### 3.2 修正

檔案頂端 import 區增加：

```ts
import { randomUUID } from 'node:crypto';
```

router middleware：

```ts
const traceId = randomUUID().slice(0, 8); // first 8 chars of a v4 UUID
```

**設計取捨：full UUID vs `slice(0, 8)`**

| 方案                | 優點                                | 缺點                                                         |
| ------------------- | ----------------------------------- | ------------------------------------------------------------ |
| `randomUUID()` 全長 | 真正全域唯一                        | 36 字元，log 視覺過長                                        |
| `slice(0, 8)`       | 與既有 log 視覺長度一致；保留分散性 | 同 process 內 10^9 筆才期望碰撞，對 Discord bot 場景遠超實際 |

採 `slice(0, 8)`：保留既有 log UX，且 UUID v4 前 8 字元為純隨機，
分散性遠高於 `Math.random().toString(36)`。

### 3.3 採用的 Design Pattern

無；屬 library swap。

### 3.4 觸及檔案

- `src/bot/index.ts`（1 行 + 1 行 import）。
- R1 完成後若 router middleware 已搬到 `ClientEventBridge`，則改在
  該檔案內；位置以 R1 收斂後為準（HLD §9 表已標註「位置一致」）。

### 3.5 測試

新增 `test/bot/trace-id.spec.ts`（檔名暫定，與 R1 後位置同步）：

| 案例 | 驗收                                                        |
| ---- | ----------------------------------------------------------- |
| 格式 | 產生 1 筆，長度 === 8，全部字元為 `/^[0-9a-f]{8}$/`         |
| 唯一 | 連續產生 1000 筆放入 `Set`，`size === 1000`（碰撞為實質零） |

Mock 策略：直接 `import { randomUUID }` 並反覆呼叫即可；不需要 mock。

## 4. R6.2 — `login()` 失敗即 reject

### 4.1 現況

`src/bot/index.ts:619-634`：

```ts
public login = async () => {
    logSystem(this.logger, this.clientId, "Logging in...");
    await this.client.login(this.token)
    .catch((err) => {
        logSystem(this.logger, this.clientId, `Failed to login: ${err}`);
    });
    if (!this.client.user) {
        logSystem(this.logger, this.clientId, "Failed to login: No user found.");
        return;
    }
    logSystem(this.logger, this.clientId, `Logged in as ${this.client.user.username}!`);
    if (this.config.admin) {
        this.adminId = this.config.admin;
    }
}
```

問題：失敗只記 log 即 resolve，`run()` 接著走 `startAll()` 與
`registerGuild()`，留下半啟動狀態 bot。

### 4.2 修正

```ts
public login = async (): Promise<void> => {
    logSystem(this.logger, this.clientId, 'Logging in...');
    try {
        await this.client.login(this.token);
    } catch (cause) {
        const error = new ConfigurationError({
            code: 'BOT_LOGIN_FAILED',
            messageKey: 'errors:bot.login_failed',
            messageParams: { clientId: this.clientId },
            cause,
        });
        logError(this.logger, error);
        throw error;
    }
    if (!this.client.user) {
        const error = new ConfigurationError({
            code: 'BOT_LOGIN_NO_USER',
            messageKey: 'errors:bot.login_no_user',
            messageParams: { clientId: this.clientId },
        });
        logError(this.logger, error);
        throw error;
    }
    logSystem(this.logger, this.clientId, `Logged in as ${this.client.user.username}!`);
    if (this.config.admin) {
        this.adminId = this.config.admin;
    }
};
```

### 4.3 i18n key

實際 grep `src/i18n/locales/zh-TW/errors.json` 後確認 `errors:bot.*`
namespace 已存在（既有 `bot_not_found`），但無 `login_failed` /
`login_no_user`。R6.2 須於同一 commit 同步新增到 **zh-TW 與 en**：

```json
{
  "bot": {
    "login_failed": "登入 Discord 失敗（{{clientId}}）",
    "login_no_user": "登入 Discord 後未取得 user（{{clientId}}）"
  }
}
```

英文 catalog 用相同 key 結構。新增 key 屬「結構性新增」，不違反
proposal §10.2 的「不刪 / 不改 i18n key」原則。

### 4.4 採用的 Design Pattern

沿用既有 `Result / DomainError` 例外傳遞慣例（design.md §2.2）。
`ConfigurationError` 本身屬 `core/errors` 既有 taxonomy。

### 4.5 觸及檔案

- `src/bot/index.ts`
- `src/i18n/locales/zh-TW/errors.json`
- `src/i18n/locales/en/errors.json`
- `test/bot/login.spec.ts`（新增）

### 4.6 測試

| 案例                | 安排                                                                      | 驗收                                                                                       |
| ------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| login reject        | mock `client.login` reject(`new Error('invalid token')`)                  | `bot.run()` 的 promise reject、type 為 `ConfigurationError`、`code === 'BOT_LOGIN_FAILED'` |
| login 成功但無 user | mock `client.login` resolve，`client.user === null`                       | reject、`code === 'BOT_LOGIN_NO_USER'`                                                     |
| 無副作用            | 上述兩案例後檢查 `host.startAll` / `registerGuild` 的 spy 皆 `not called` | 確認 `run()` 在 login 失敗即中止                                                           |
| happy path 回歸     | login resolve、user 存在                                                  | 既有測試保持綠                                                                             |

Mock 策略：用 `vi.fn()` stub `client.login`、`host.startAll`；
`client.user` 用 getter mock。

類別定義：

- **a**：trivial replace 為 `bot.logger.info / warn / error`（handler 內部，logger 取得來源為 `bot` 或 `interaction.client` cast）。

### 5.2 修正策略（依類別）

```ts
// (a) handler 內
bot.logger.info({ event: 'hourTPE' }, `hourTPE=${hourTPE}`);

// (b) deploy 腳本
import { createBootstrapLogger } from './core/config/bootstrap-logger';
const logger = createBootstrapLogger('deploy');
logger.warn({ command: name }, 'Command could not be created or has no config.');

// (c) last-resort fallback（保留 console，需配 ESLint allowed exception）
try {
  /* ... */
} catch (err) {
  // last-resort: bootstrap logger unavailable in top-level catch
  console.error(err);
}

// (d) 直接刪除
```

### 5.3 ESLint 規則

`eslint.config.mjs`（src/ 全域 block）：

```js
// before
'no-console': ['warn', { allow: ['warn', 'error'] }],

// after
'no-console': ['error', { allow: ['error'] }],
```

`allow: ['error']` 是給類別 (c) 的最終 fallback 用；其他 level 一律走
logger。test 與 scripts 已在既有 config 內 `'no-console': 'off'`，
不動。

## 8. 跨子項依賴與時機

```text
R1 (BaseBot 拆解)
  ├─ commit 內：R6.5（import 區整理 + import/first 規則）
  ├─ commit 後：R6.4（命名一致化，獨立 commit）
  └─ 之後依序：R6.1 → R6.2 → R6.3
```

| 子項 | 時機                                 | 理由                                                 |
| ---- | ------------------------------------ | ---------------------------------------------------- |
| R6.5 | 與 R1 同 commit 或緊接其後           | R1 必然改 import；同步做避免雙重 diff                |
| R6.4 | R1 全部 commit 落地後，獨立一 commit | TypeScript rename 是大面 diff；獨立 commit 易 review |
| R6.1 | R1 之後任何時機                      | 位置可能因 R1 移到 `ClientEventBridge`               |
| R6.2 | R1 之後任何時機                      | 與 R1 的 lifecycle 改寫無耦合                        |
| R6.3 | R6 系列最後                          | 避免 R6.1 / R6.2 過程中新寫入 `console.*`            |

## 10. 與其他 R 的整合點

- **R1**：R6.4 / R6.5 必須與 R1 同分支；R6.5 與 R1 第一個 commit 同
  步；R6.4 在 R1 全數 commit 之後獨立 commit。R6.1 / R6.2 雖無強耦
  合，但若 R1 將 router middleware / login 流程搬到 collaborator，
  R6.1 / R6.2 的修改位置改在新類別內。
- **R3 / R4**：共用 `eslint.config.mjs`；R6.3（`no-console: error`）
  與 R6.5（`import/first: error`）的 rule 變更應與 R3 / R4 的 ESLint
  變更合併在同一 commit 或彼此前後緊鄰，避免 lint 規則來回擾動。
  建議順序：R3 → R4 → R6.3 → R6.5（lint rule 一次到位）。
- **R5**：彼此獨立。

## 11. 不做的設計決策

- **不替換 logger**：pino 維持；R6.3 僅做 console → 既有 logger 的
  替換，不評估其他 logger library。
- **不引入 `AsyncLocalStorage` 做 traceId 傳遞**：R6.1 僅升級隨機源；
  跨 await 自動傳遞 traceId 屬另一層架構議題，超出 R6 scope。
- **R6.4 不擴及 BaseBot 以外**：codebase 仍有其他 snake_case 殘餘
  （如 `bot_name`、`button_type`、`ssm_type`、`modal_type`）；這些屬
  Discord interaction custom_id 解析鏈或 GuildInfo 結構，動到會牽
  涉 catalog / handler 簽名，明確不在 R6.4 範圍內。
- **R6.5 不啟用 `import/order`**：僅啟用 `import/first`；`import/order`
  的 group 排序爭議大且會擴散 diff，留待日後另議。
- **R6.3 不刪除 `process.stderr.write` 之類非 `console.*` 的低階輸出**：
  ESLint `no-console` 只管 `console`；其他輸出方式不在規則覆蓋面內，
  本輪不掃。
