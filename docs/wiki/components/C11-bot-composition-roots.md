# C11 — Bot Composition Roots

## Responsibility

The only wiring layer. `BaseBot` owns the lifecycle; each personality picks its plugins and middlewares; `src/deploy.ts` handles slash-command registration. Composition roots are the only place that may import directly from `@core/ioc`.

## `BaseBot` and collaborators

`src/bot/index.ts` keeps `BaseBot` as a thin lifecycle owner. `run()` orchestrates four collaborators in order: set up the container, set up the translator (in the bot's configured `language`, see below), connect every guild's DB, register every guild, attach the client event bridge, then start the plugin host.

- `src/bot/guild-registrar.ts` — `GuildRegistrar` assembles `GuildInfo` from Discord guild objects. Pure assembly; opens no Mongo connection and sends no Discord traffic.
- `src/bot/client-event-bridge.ts` — `ClientEventBridge` adapts raw `client.on(...)` events into router dispatch, `EventDispatcher` emits, and `ReactionHandlerPort` calls. Single `attach` / `detach` entry; attaching twice throws `TypeError` as a contract violation.
- `src/bot/guild-db-connector.ts` — `GuildDbConnector` fans out per-guild Mongo connections. `connectAll` is resilient: a single guild's failure is logged but does not abort the others.
- `src/bot/guild-onboarding.ts` — `BaseBotGuildOnboardingPort` adapts `BaseBot` to `GuildOnboardingPort` (registered as `TOKENS.GuildOnboardingPort`) so the `guild-events` plugin can drive new-guild onboarding without depending on `BaseBot` directly.
- `src/bot/locales-dir.ts` — `resolveLocalesDir()` helper. The composition root owns the locales path and injects it into `BaseBot` via the constructor; the core i18n layer no longer guesses it from `__dirname`.
- `src/bot/middlewares.ts` — shared router middlewares (request-scoped `traceId`, structured-log binding).

Subclasses override the protected `eventBridgeSuppression()` hook to opt out of raw listeners they do not need (e.g. `konata`, `msg-archive`). `BaseBot.login` rejects with `ConfigurationError` (`BOT_LOGIN_FAILED` / `BOT_LOGIN_NO_USER`) on failure; `run()` never proceeds with a half-attached client. On success it emits one `ops:bot.online` system line naming the bot's Discord `displayName`, giving operators a per-personality "who am I" marker at startup.

`setupContainer` (the first `run()` step, before login) installs two process-level safety nets so both span the client's whole lifecycle — including login and shutdown, which the late-attaching / early-detaching `ClientEventBridge` cannot cover: `installProcessHandlers` (C1, `src/core/logger/process-handlers.ts`) and `installClientSafetyListeners` (`src/bot/client-safety-listeners.ts`). The latter attaches non-fatal `error` / `shardError` / `shardDisconnect` listeners to the Discord client; without an `error` listener Node rethrows an emitted client error as an `uncaughtException`, so a transient gateway socket reset (ECONNRESET / "socket hang up") would otherwise crash the whole process instead of being logged while discord.js reconnects.

## Optional plugin singletons

`bot.voice`, `bot.modelCatalog`, and `bot.defaultModelResolver` are getters backed by `container.tryResolve(TOKENS.VoiceController)`, `container.tryResolve(TOKENS.ModelCatalog)`, and `container.tryResolve(TOKENS.DefaultModelResolver)`. Bots that do not load the registering plugin (for example `msg-archive`) naturally observe `undefined`. Handler-level disabled-guild checks read `bot.connectionManager.isDisabled(...)` rather than any `BaseBot`-owned map.

`bot.permissionRankPolicy` is a getter backed by `container.tryResolve(TOKENS.PermissionRankPolicy)`. Unlike the plugin singletons above it is registered eagerly in the `BaseBot` constructor (never plugin-gated), so it is present for any bot with a `guilds` config; `undefined` only inside the pre-`run()` window. The `/traffic` handler (C6) reaches the privacy/clearance ranking through this accessor rather than touching the container.

## Personalities

- `src/bot/nijika/` — web-facing. Loads `createEarthquakePlugin({ port })`, which owns the Express `/discord/earthquake` route and per-guild broadcast. Also loads `createSocialLinkPreviewPlugin(config.social_link_preview)` — the social-link preview (C8), optional, defaulted in code (disabled by default). Channel suppression for guild-events / social-link-preview / channel-logging now comes from the per-guild `permission_rank` block via `TOKENS.PermissionRankPolicy` (C1), not a personality-level `blocked_channels` list. (The self-hosted-LLM auto-reply formerly loaded here now lives in the `gopher` personality.)
- `src/bot/konata/` — interactive personality.
- `src/bot/tomori/` — interactive personality.
- `src/bot/msg-archive/` — worker-style. Suppresses interaction / reaction / `guildCreate` listeners via `eventBridgeSuppression()` and runs `MessageBackupPlugin`. Backup transcripts go to `logs/backup/msg-archive-<guildId>-<YYYY-MM-DD_HH-MM-SS>.log` (one timestamped file per run, so reruns never overwrite a prior transcript). Its `config.json` carries an optional `backup_interval_minutes` (defaults to 60); the root converts it to the plugin's `backupIntervalMs`.
- `src/bot/gopher/` — focused, **database-free** personality (Discord display name "老鼠人"). Constructed with an empty `mongoURI` and `loadEnv({ requireDb: false })`; `BaseBot` treats an empty `mongoURI` as "no DB" (so `TOKENS.Env` still binds, the guild-DB fan-out short-circuits, and `shutdown` skips the connection-manager close). Loads the ported `createLlmAutoReplyPlugin(config.llm_auto_reply, { endpointProvider })` (C8) — the self-hosted-LLM auto-reply moved here from `nijika` (gopher applies no channel exclusions); `createSettingsApiPlugin(config.settings_api, { port, apiKey, getEndpoint, setEndpoint })` (C8); and `createIdentitySyncPlugin(config.identity_sync)` (C8). Registers only the `/help` command. `src/bot/gopher/settings-store.ts` (`GopherSettingsStore`) is the single owner of the runtime-mutable `endpoint`: it is seeded at boot from the already-imported `llm_auto_reply` block the composition root passes in (construction does no filesystem I/O — so it never depends on the gitignored `config.json` existing, which keeps the pure composition test from booting a disk read), hands `getEndpoint` to the auto-reply plugin (via `endpointProvider`) and to the settings API, and `setEndpoint` swaps the in-memory value then rewrites `config.json` (preserving other keys, 2-space indent). The settings API's bearer key comes from `Env.GOPHER_SETTINGS_API_KEY` (`.env`), never `config.json`; `PORT` carries the API's listen port.

## Bot `config.json`

Each personality loads a sibling `config.json` (`import config from './config.json'`) and passes it to its constructor; the shape is `Config` in `src/bot/index.ts` plus any per-personality extension. There is no runtime schema validation — the composition root trusts its own file — but several fields have deliberate semantics:

- `admin` — optional `string[]` of Discord user ids granted bot-admin privileges. The constructor copies it into `BaseBot.adminIds` (default `[]`); `bot.isAdmin(userId)` is the single membership check the admin-gated handlers (`/ai_whitelist_*`) use, and `/bug_report` DMs every id in the list. Snowflake ids exceed JS's safe-integer range, so they must be JSON strings.
- `language` — optional default display locale (`'zh-TW'` | `'en'`; omit for the framework default `zh-TW`). `BaseBot.buildHost` validates it with `isLocale` and passes it to `createDefaultTranslator({ fallbackLocale })`; an unsupported value logs a warning and falls back to the default. All four bundled bots set `"language": "zh-TW"` explicitly.
- `guilds.<id>.channels` and `guilds.<id>.roles` — both optional. A guild may omit either map, or omit its whole `guilds` entry. `GuildRegistrar` resolves a missing map to `{}` and drops ids that are not in the live cache, so the bot keeps every feature but silently skips channel-bound side effects (the `debug` interaction log and the `guild-events` mirror have nothing to send to). `tomori` runs this way — its `config.json` has no `guilds` block at all. (`msg-archive` is the exception: `MessageBackupPlugin` requires a `debug` channel and aborts a backup pass without one — by design.)
- `guilds.<id>.permission_rank` — optional. Operator-defined privacy / clearance ranks for this guild, consumed by `TOKENS.PermissionRankPolicy` (C1). `channels` maps `channelId -> int rank ≥ 0` (higher = more private; an unlisted channel is rank 0); `roles` maps `roleId -> int rank ≥ 0` (a member's clearance is the max over their ranked roles); `features` sets a per-feature `maxChannelRank` ceiling. A feature suppresses a channel when its effective rank — `max(channel rank, parent-thread rank)` — exceeds that feature's ceiling (`null` = unbounded = never suppress). Code defaults: `guild_events` = `0`, `channel_logging` = `0` (mirror / log only rank-0 channels), `social_preview` = `null` (preview everywhere). The `roles` map here is keyed by raw Discord role id (the form `member.roles.cache.keys()` yields), deliberately distinct from the symbolic-name `roles` map above that feeds `GuildRegistry.getRole`. Unlike the rest of the config root this block IS validated — a malformed entry fails fast at startup naming the offending guild. Replaces the former top-level `blocked_channels` list (removed); suppression scope is now per-guild rather than bot-wide.
- `llm_auto_reply` — optional block consumed by `gopher`'s `createLlmAutoReplyPlugin` (C8). All fields are defaulted in code (`src/plugins/llm-auto-reply/config.ts`, zod `.strict()`), so the block may be partial or omitted entirely: `enabled` (bool, default `false` — strictly opt-in), `probability` (0..1, default `0.05`), `messageCount` (N most-recent messages to require, default `5`), `windowSeconds` (the N must span ≤ this, default `30`), `cooldownSeconds` (minimum gap between consecutive automatic replies in a channel, default `30`; `0` disables; an @-mention skips it but still records it), `endpoint` (self-hosted chat URL, default a non-functional placeholder), `timeoutMs` (per-request, default `10000`). An unknown key fails fast at startup. `gopher`'s live `config.json` enables it and points `endpoint` at the deployment's self-hosted host; that URL changes when the host moves, so it is updated at runtime through `gopher`'s settings API (which writes the new value back to this block) rather than requiring a restart.
- `settings_api` — optional block consumed by `gopher`'s `createSettingsApiPlugin` (C8). Defaulted in code (`src/plugins/settings-api/config.ts`, zod `.strict()`): `enabled` (bool, default `false`), `host` (bind interface, default `127.0.0.1` — loopback-only is the safe default; set `0.0.0.0` for remote use behind a firewall), `basePath` (URL prefix, must start with `/`, default `/settings`). The bearer key is **not** here — it is read from `Env.GOPHER_SETTINGS_API_KEY`; an enabled API with no key refuses to start. The listen port is `Env.PORT`.
- `identity_sync` — optional block consumed by `gopher`'s `createIdentitySyncPlugin` (C8). Defaulted in code (`src/plugins/identity-sync/config.ts`, zod `.strict()`): `enabled` (bool, default `false`), `syncWithSource` (bool, default `false` — `true` mirrors a source user daily, `false` applies the static fallback), `sourceUserId` (required when `enabled && syncWithSource`), `schedule` (daily cron, default `0 4 * * *`), `syncAvatar` / `syncNickname` (bools, default `true`), `fallbackNickname` (default empty = leave untouched; the CJK display name "老鼠人" is set here in `config.json` so it never appears in a `.ts` source), `fallbackAvatarPath` (local file or URL, default `assets/gopher.png`).
- `social_link_preview` — optional block consumed by `nijika`'s `createSocialLinkPreviewPlugin` (C8). All fields are defaulted in code (`src/plugins/social-link-preview/config.ts`, zod `.strict()`), so the block may be partial or omitted entirely: `enabled` (bool, default `false` — strictly opt-in), `originalMessageStrategy` (`suppress` | `delete` | `leave`, default `suppress`), `providers` (optional allow-list / kill-switch over `twitter`, `instagram`, `threads`, `facebook`, `reddit`, `bahamut`, `bilibili`; omitted = all), `timeoutMs` (per-host OpenGraph probe, default `4000`), `validationBudgetMs` (cumulative probe budget per URL, default `8000`), `maxUrlsPerMessage` (previews per message, default `1`), and the per-source embed-proxy **host lists** `twitterProxyHosts` / `instagramProxyHosts` / `threadsProxyHosts` / `facebookProxyHosts` / `redditProxyHosts` / `bilibiliProxyHosts` (non-empty arrays, probed in order; defaults `[fxtwitter.com, vxtwitter.com]` / `[kkinstagram.com, uuinstagram.com]` / `[viewthreads.com, vxthreads.net]` / `[facebed.com, fixacebook.com]` / `[vxreddit.com, rxddit.com]` / `[vxbilibili.com, bilibiliez.com]`). An unknown key fails fast at startup (the pre-v2 scalar `*ProxyHost` keys are intentionally rejected). Each rewrite provider probes its list (Discord crawler UA) and posts the first host that yields media — video > image > text — or nothing if none do, so a dead proxy never leaves a bare link. `suppress` / `delete` require the bot to hold `ManageMessages`; without it the feature degrades to reply-only.

## Deploy

`src/deploy.ts` is the slash-command registration entry point. It uses the same `resolveLocalesDir()` helper as `BaseBot` to inject the locales path and emits structured pino through `createBootstrapLogger({ component: 'deploy' }, { fileRouter: false })` — console-only. As a one-shot CLI it has no `bot` binding (which the file router requires) and must not create a `logs/<botId>/` tree, so it opts out of the file sink.

Command descriptions are localised to the bot's `config.language` via `buildDeployTranslator` (same `fallbackLocale` plumbing as `BaseBot.buildHost`), so a bot's registered slash-command text matches its runtime locale. The `--dry-run` flag builds and prints the resolved command name/description without registering, which isolates code behaviour from Discord's global-command propagation delay (up to ~1h).

The default global deploy registers the global set **and then prunes guild-scoped commands** from every guild (`clearAllGuildCommands`), because a leftover guild-scoped registration overrides the global one in that guild and would otherwise keep showing stale commands/text. The guild list is fetched with `fetchAllUserGuilds` (`src/deploy-guilds.ts`), which follows Discord's 200-per-page `after` cursor so bots in more than 200 guilds are fully covered. The prune walk runs sequentially under the Discord rate limit (`PER_ITER_DELAY_MS`, `rateLimited` listener); `--keep-guild-commands` skips it for large bots or intentional guild commands, and `--cleanup-guild-commands` runs only the prune.
