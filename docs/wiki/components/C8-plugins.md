# C8 — Plugins

## Responsibility

Self-contained business features. Every behavior that touches Discord users or guild state lives here. Each plugin satisfies the `Plugin<Config>` contract (see C3) and is opted into a personality through `this.use(...)` inside the bot subclass.

## The fourteen plugins

- `src/plugins/auto-reply/` — keyword-triggered replies.
- `src/plugins/llm-chat/` — LLM chat. Registers `TOKENS.ModelCatalog` and `TOKENS.DefaultModelResolver` during `init` via `ctx.registerInstance(...)`. `onReady` kicks off an initial background `DefaultModelResolver.refresh()` and schedules a weekly refresh (Monday 04:00, cron `0 4 * * 1`) via `JobManager.scheduleRecurring`, so a model going legacy never strands the whitelist-entry default.
- `src/plugins/message-backup/` — periodic message archival; the only plugin used by the `msg-archive` worker. The repeat cadence is configurable: `MessageBackupPluginConfig.backupIntervalMs` (optional, defaults to one hour), fed from the `msg-archive` composition root's operator-facing `backup_interval_minutes` config field. The per-run transcript log (`logs/backup/msg-archive-<guildId>-<stamp>.log`) is **opt-in, default off**: `MessageBackupPluginConfig.backupLogEnabled` (default `false`, fed from the `backup_log_enabled` config field) only gates whether `performBackup` writes that transcript — when off it uses a `NullBackupLog` (Null Object) so the backup itself (DB ingest, debug-channel status) runs identically but no `logs/backup/` file or directory is created. The `setTimeout` repeat loop is failure-isolated: each guild's pass is wrapped in its own `try/catch` (one guild's error never aborts the others in the pass), and the loop body always reschedules itself in a `finally`, so a thrown pass is logged rather than silently killing the loop or leaking an `unhandledRejection`.
- `src/plugins/giveaway/` — giveaway scheduling and reaction tally; `/giveaway_create` opens a modal (four text inputs — duration / prize / winner_num / description — handled by the `giveaway_create` modal handler) and the announcement is published in the channel the command is invoked from (no dedicated `giveaway` channel config). `/giveaway_delete` lists the guild's active giveaways as a `giveaway_delete` string-select (paged at 25 options per row) and deletes the selected one, so no message id needs to be copied. Uses `JobManager` and `parseDuration` from `@core/scheduling`.
- `src/plugins/temp-role/` — temporary, permission-less notification roles created via `/temp_role`. `createTempRole` makes a mentionable role with no permissions, posts a claim message whose button reuses the existing `toggle_role|<roleId>` custom id (so any member can self-claim / release it), persists the row, and schedules a one-shot expiry job (`JobManager` from `@core/scheduling`; selectable lifetime with a hard 30-day cap, default 30). On expiry the role is deleted, the claim message is edited to its expired state (button stripped), and the row removed; `rebootTempRoleJobs` rebuilds pending jobs and immediately expires past-due rows on boot, mirroring the giveaway scheduler. Expiry comparisons use the injected `Clock`. Open to every member by design — the role grants nothing — guarded by a 250-role-per-guild ceiling. Loaded by the `nijika` and `tomori` personalities.
- `src/plugins/activity/` — activity tracking and leaderboards. Shares the same `@core/scheduling` helpers.
- `src/plugins/guild-events/` — subscribes to `messageUpdate`, `messageDelete`, `guildMemberUpdate`, and `guildCreate`. Mirrors message edits/deletes and role changes to the guild's configured `event` channel and emits matching `logGuildEvent` audit lines; the audit lines are decoupled from the `event` channel, so they fire even when no `event` channel is configured. On `guildCreate` it resolves `TOKENS.GuildOnboardingPort` and calls it to connect the new guild's DB and register its commands. Failures are logged structured, never re-thrown. The `guild_events` rank ceiling gates **Discord disclosure only**, via `TOKENS.PermissionRankPolicy` (default ceiling `0`, i.e. only rank-0 channels are mirrored to the `event` channel); the channel's full ancestry is folded in (`max` over channel → parent channel → category, so a thread under a ranked category counts as ranked too). The **local record is unconditional**: for every non-bot edit/delete, regardless of rank, the `logGuildEvent` audit line is written to `logs/<bot>/<guildId>/<YYYY-MM-DD>.log` and deleted attachments are downloaded to `./data/deleted_attachments/<guildId>/`. So a rank-1+ private channel's edits/deletes are fully recorded server-side (text + attachments) yet never disclosed on Discord — meaning anyone with file-system access to the bot host can read private-channel content (see [decision 0009](../../history/0009-guild-events-local-record-decoupling.md)). A partial message whose `fetch()` rejects (a deleted, uncached message) is still recorded from cache. Loaded by the `nijika` and `tomori` personalities.
- `src/plugins/voice/` — voice-channel controller. Registers `TOKENS.VoiceController` during `init`.
- `src/plugins/earthquake/` — Express `/discord/earthquake` route plus per-guild broadcast; `scope='bot'`. Owned by the `nijika` personality (see C11). The HTTP socket is closed in `onShutdown`; broadcast logic lives in `internal/broadcast.ts`.
- `src/plugins/llm-auto-reply/` — `messageCreate` subscriber that occasionally (configured `probability`) injects a context-aware reply from a self-hosted LLM. Rolls the probability gate before any fetch; on a hit it fetches the latest `messageCount` messages, requires they form a burst within `windowSeconds`, builds a transcript (bot/blank lines dropped; each surviving line is `<displayName>: <content>` with no channel-name prefix), POSTs it via `SelfHostedLlmClient` (C5), and posts one reply with mentions suppressed. The reply is a single message (`internal/reply.ts`): a blank LLM reply is skipped and an over-long one is truncated to Discord's 2000-char limit (rather than split) so `channel.send` cannot reject it. A per-channel cooldown (`internal/cooldown.ts`, `ReplyCooldown`, `cooldownSeconds`) enforces a minimum gap between consecutive automatic replies in a channel; `0` disables it. To stay correct under concurrent `messageCreate` handlers (events are dispatched fire-and-forget, so handlers interleave at every `await`), the channel is marked in-flight before the first await — a concurrent automatic message in the same channel yields — and the cooldown is recorded only when a reply actually goes out (so a no-op attempt does not suppress the next reply); `ReplyCooldown.record` is monotonic. The in-flight tracker (`internal/in-flight.ts`, `InFlightChannels`) is reference-counted, because an @-mention reply bypasses the in-flight check but still occupies the channel — so two attempts can overlap, and the channel must stay busy until the last one finishes rather than being cleared by the first. A message that @-mentions the bot (`internal/trigger.ts`, `mentionsBot`, mirroring konata's llm-chat — `message.mentions.has(clientId, { ignoreRepliedUser: true })`, so a _reply_ to the bot is not treated as a fresh @-tag) bypasses the probability gate, the `windowSeconds` burst check, and the cooldown — the `messageCount` requirement and all other guards (enabled, bot author, guild-only, blocked channels) still apply — and the bot's mention is stripped from the transcript so the control marker never reaches the prompt. The probabilistic automatic reply is unchanged. Every posted reply (automatic or @-mention) records the cooldown, so a following automatic reply still observes the gap. Settings come from the bot's `llm_auto_reply` config block (`config.ts`, zod defaults in code); the optional `blockedChannels` dep — a list-based exclusion that intentionally predates the `permission_rank` model — excludes channels from triggering (gopher passes none). The live `endpoint` is read through an injected `endpointProvider` (rather than baked into the client) so `gopher`'s settings API can swap it at runtime (see C11). Owned by the `gopher` personality (see C11); `scope='bot'`. Pure helpers (`buildTranscript`, `isWithinWindow`, the trigger + cooldown helpers) and the orchestrator live in `internal/`.
- `src/plugins/social-link-preview/` — `messageCreate` subscriber that detects social-media share links (Twitter/X, Instagram, Threads, Facebook, Reddit, Bahamut, Bilibili), posts a richer preview, and handles the user's original auto-embed. Hybrid mechanism via the link-preview Provider Strategy (C5): video-capable sources are rewritten to an embed-proxy domain so Discord unfurls a playable video; Bahamut (no proxy) is scraped for OpenGraph and rendered as a static embed. Facebook additionally expands `/share/<type>/<token>` short links — whose opaque token the proxies cannot resolve — to their canonical permalink before proxying, and falls back to a static OpenGraph card (scraped from Facebook itself) when no proxy can preview the link (see C5); Threads expands its own `/share/<token>` links to the `/@user/post/<id>` permalink the same way, but with no card fallback — an unresolvable share link is skipped silently, since threads.com answers the crawler with the same login wall a proxy would (see C5). `internal/orchestrator.ts` extracts candidate URLs (`extract-urls.ts`, which strips tracking / share-attribution query params — `mibextid`, `utm_*`, `fbclid`, `igsh`, ... via a denylist that preserves meaningful params like Facebook `v` / Bahamut `sn` — de-duplicates, honours angle-bracket `<url>` opt-out, and is bounded by a hard scan limit), routes each through the registry, renders the reply (`render.ts`, branching on the result union, always `allowedMentions: { parse: [] }`), and applies the `originalMessageStrategy` (`suppress.ts`). The number of previews per message is capped by `maxUrlsPerMessage`. `originalMessageStrategy` (`suppress` / `delete` / `leave`, default `suppress`) needs `ManageMessages`; when the permission is missing the original is left intact and the fact is logged at debug level — the feature degrades to reply-only and never throws out of the handler. Every per-URL failure is silent to the channel (provider `Err` logged + skipped, `null` skipped). Settings come from the bot's `social_link_preview` config block (`config.ts`, zod `.strict()`, opt-in `enabled: false`). Its scalars default in code, but the six per-source embed-proxy **host lists** are operator configuration with **no code defaults** and become mandatory the moment `enabled` is `true` — a missing list fails startup naming the key, and a disabled bot builds no registry at all, since it supplies no hosts to build one from. Probing and ranking those hosts is C5's business (validate-before-posting, `video > image > weak-image > text`); the config keys and the recommended values are in C11. Channel suppression comes from `TOKENS.PermissionRankPolicy` (the `social_preview` feature; default ceiling is unbounded, so previews fire in every channel unless an operator sets a finite `maxChannelRank` for `social_preview` in `permission_rank`). Loaded by the `nijika` and `tomori` personalities (see C11); `scope='bot'`, non-critical.
- `src/plugins/settings-api/` — owner-only HTTP REST API (Express) to read/update runtime-mutable settings and persist them. Today the only mutable field is the self-hosted LLM `endpoint`: `GET {basePath}/endpoint` returns it, `PUT {basePath}/endpoint` validates a `{ endpoint: <url> }` body (zod, 400 on failure) and calls the injected `setEndpoint`. Every request must carry `Authorization: Bearer <key>`, compared in constant time (`timingSafeEqual`); the key is injected from `Env.GOPHER_SETTINGS_API_KEY` (never `config.json`). When enabled but no key is configured the server refuses to start (fail-closed); bind host (`config.host`, default `127.0.0.1`) and `basePath` come from the `settings_api` config block (`config.ts`). The runtime endpoint cell + `config.json` persistence live in the composition root and are injected as `getEndpoint`/`setEndpoint` (see C11), so the plugin never touches the filesystem. Owned by the `gopher` personality; `scope='bot'`, non-critical. The socket is closed in `onShutdown`.
- `src/plugins/x-media-feed/` — periodic poller that forwards new **image / video** posts from followed X (Twitter) accounts into a guild's configured feed channel. Reads timelines through the `XTimelineSource` Strategy (C5, default `FxTwitterTimelineSource`) and posts a plain-text line carrying an embed-proxy link (`embedProxyHost`, default `fxtwitter.com`) so **Discord** unfurls a playable video — a bot-authored embed cannot render one — which also means no media is downloaded or re-uploaded. `onReady` runs one pass immediately then drives a self-rescheduling `setTimeout` loop (`pollIntervalMs`), mirroring `message-backup`; `contributes.jobs` is deliberately unused because the host merges only handler contributions, so a job declared there would never run. `internal/filter.ts` keeps only the account's **own, original, media-carrying** posts: reposts are rejected by the upstream's `reposted_by` marker _and_ by an independent author comparison (a repost entry carries the original author), replies — including the account's own thread continuations — are dropped, and text-only posts are dropped. De-duplication is by `BigInt` post-id comparison against a per-handle cursor (`XFeedCursorRepo`, C4); post ids exceed `Number.MAX_SAFE_INTEGER`, so a numeric comparison would collapse distinct ids. **Cursor discipline** is the load-bearing invariant: the cursor advances only past posts that actually reached Discord (the advance happens in a `finally`, so a mid-run send failure still records the progress already made and the rest is retried next pass), the per-pass cap takes the **oldest** eligible posts so a backlog is never stepped over, and the very first pass for a handle only seeds a baseline — it never backfills an existing timeline into the channel. That baseline is the highest id on the page **including reposts and replies** (X ids are globally time-ordered, so it sits at or above everything already published): anchoring on the account's own posts alone would leave a repost-only page with no cursor, and the _next_ pass would then consume the account's first genuinely new post as its baseline instead of forwarding it. An empty timeline has no id to anchor on and instead seeds a **clock-derived snowflake floor** (`(now - X's epoch) << 22`) — above everything already published, below everything published afterwards. A plain `0` would sit below every post ever written, so the next full sweep (which drops `since` and returns the whole page) would drain the account's back catalogue into the channel. Every `fullSweepEveryPolls`-th pass drops the upstream `since` parameter and re-reads the whole timeline, because `since` is a strict `>`: a post created in the same second as the newest one already forwarded would otherwise stay invisible forever, and the sweep turns that permanent miss into a bounded delay. Failure isolation is layered — per account inside a pass, per pass in the loop's `finally` — so no guild, account, repository read, or send can stop the poller. On every boot, before the first pass, a reconciliation sweep (`internal/reconcile.ts`) deletes each guild's cursors whose handle is no longer in `accounts`, so the stored state stays an exact mirror of the configuration — re-adding a removed account therefore behaves like a brand-new one (fresh baseline, no gap backfill), and a case-only handle change counts as remove-plus-add because the store is keyed by the exact configured string. A guild without the configured feed channel silently opts out, and because the channel is resolved **before** the timeline is read, such a guild costs no upstream request and gets no cursor — so it starts cleanly whenever it does opt in, rather than from a cursor frozen at whenever the plugin was first enabled. Settings come from the bot's `x_media_feed` config block (`config.ts`, zod defaults, opt-in `enabled: false`); loaded by the `nijika` personality (see C11); `scope='bot'`, non-critical.
- `src/plugins/identity-sync/` — keeps the bot's avatar + per-guild nickname aligned, re-checked once per day. On `onReady` it applies the identity once and schedules a daily cron via `JobManager.scheduleRecurring` (`@core/scheduling`), cancelled in `onShutdown`. In sync mode (`syncWithSource: true`) it mirrors a source user (`sourceUserId`): the bot's nickname in each guild is set to the source user's **per-guild server nickname** there (`GuildMember.displayName` = nickname ?? global name, resolved separately per guild — not the source's global `User.displayName`), and the bot's global avatar mirrors the source user's global avatar, the latter guarded by the last-applied source avatar hash so an unchanged avatar is never re-uploaded (Discord rate-limits `PATCH /users/@me`). In fallback mode it applies a static identity — `fallbackNickname` (sourced from `config.json`, so the CJK literal stays out of `.ts`) and `fallbackAvatarPath` (a local file or URL), the avatar applied once per process. The apply routine lives in `internal/sync.ts`. Owned by the `gopher` personality; `scope='bot'`, non-critical.

## IoC contract for plugins

Every `src/plugins/*/plugin.ts` imports `TOKENS` from the `@core/plugin` barrel:

```ts
import { TOKENS } from '../../core/plugin';
```

Direct imports of `core/ioc` or `@core/ioc` are blocked by an ESLint `no-restricted-imports` rule on `src/plugins/**`. The container's write surface is reachable only through `PluginInitContext.registerInstance(token, instance)` during `init`; the type system hides that method in later phases.

## Notes

`BaseBot.listen` checks `dispatcherSubscribesTo('guildCreate')` and skips its own `client.on(GuildCreate)` when the `guild-events` plugin already owns onboarding, avoiding double initialization. Logging is uniformly structured: no `console.*` appears under `src/plugins/`.
